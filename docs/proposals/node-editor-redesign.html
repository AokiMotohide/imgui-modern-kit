imgui-modern-kit · imkit::node_editor · Version4.1 時点の調査

Node Editor 刷新計画

Blenderのシェーダー／ジオメトリノード、Unrealのブループリント、imgui-node-editorのような使い方を、1つのUI部品で組めるようにするための現状調査と改善案です。実装はまだ行っていません。

対象: include/imkit/node_editor.h (415行)src/node_editor.cpp (2093行)src/node_layout.cpp (531行)調査日 2026-11-03

結論

グラフ編集の「中身」はすでに実用水準です。足りないのは、ノードとピンの見た目の語彙と、ホストが描画を差し替える口です。

強い編集の契約

型付きID、完全な編集要求バッチ、Begin/Update/Commit/Cancel、3段階の接続判定、動的・可変長ソケット、整列と自動配置、サブグラフ、プレビュー需要の通知。

弱い見た目の自由度

ノードは常に「角丸矩形＋ヘッダー帯＋上端の線」1種類。Reroute・Note・Subgraphにも専用の外観がない。ヘッダー色をノード単位・カテゴリ単位で指定する項目がない。

不足実行フローの表現

実行ピン（白い矢印型）、配列・参照・ワイルドカード、複数入力ソケット、未接続の中空表示、配線ハイライト、実行中の流れ表示がない。Unreal系の分岐ノードを素直に描けない。

現行の構成

公開APIはすべて imkit::node_editor にあり、グラフはホストが所有して毎フレーム GraphView として貸し出します。見た目に関わる型だけを抜き出すと次のとおりです。

確認した問題

コードを読んで確認した具体的な不足と不具合です。行番号は Version4.1（871f3b5）時点です。

高Reroute・Note・Subgraph が通常ノードと同じ矩形で描かれる

src/node_editor.cpp:636-651 の背景描画は Frame/Group かどうかしか見ていない。Reroute は240×240の空ノードになり、配線の中継点として使えない。

高実行フロー用のピンと配線がない

PinShape は Circle/Square/Diamond/Triangle の4種。実行ピンの形、太い白い配線、分岐ノードの True/False 出力をデータピンと区別して描く手段がない。

高ノード・ピン・配線の描画を差し替える口がない

見た目を変える方法は NodeView::style で NodeStyle を丸ごと渡すことだけ。SkinPart にもノード系の部位がなく、他部品と同じ水準のカスタマイズができない。

中ステータス行が常に表示される

EndNode（src/node_editor.cpp:741-758）が、status を使わないホストでも「Idle 0.00 ms」をノード下端に描く。素材ノードや設定ノードでは雑音になる。

中配線の既定色が型色ではなく accent

Link（:1157）は link.color が空なら accent。ピンは SocketTypeView の色を使うので、ピンと配線の色が食い違う。

中すべての配線に矢印が付く

曲線の75%地点に固定の三角を描く（:1166-1174）。データフロー系のエディタでは通常付けないが、消す設定がない。

中ヘッダー色をノード単位で指定できない

MakeNodeStyle はヘッダーを常に surfaceRaised にし、上端に accent の線を引く。Galleryの色変更はホスト側で NodeStyle を作り直している。

中Bypass・Disabled の状態が見た目に出ない

状態はステータス行の文字だけ。ノード全体の減光、素通し線、無効化の斜線などがない。

低リサイズつまみがズームに追従しない

EndNode（:760-767）の14pxは画面座標固定。拡大時は小さく、縮小時はノードに対して大きすぎる。

低配線ラベルに背景がない

ラベルは曲線中央に muted 色の文字だけを描くので、グリッドや他の配線と重なると読めない。

ノード形状カタログ

追加・整理したいノードの形です。1枚目が現行の唯一の形で、残りは新しく描けるようにする形です。すべて NodeShape と意味tokenで切り替え、色はテーマとカテゴリから決まります。

ピンと配線

ピンの種類

形（Shape）とは別に、役割（データか実行フローか）と入れ物（単体・配列・Set・Map）と修飾（参照・ワイルドカード・Field）を持たせます。未接続のピンは中空にするかどうかをスタイルで選べます。

配線の表現

カスタマイズ層

他の部品と同じ3段で見た目を決めます。上の段ほど簡単で、下の段ほど自由です。

段ホストがすること使う型例
1. テーマTheme を変えるだけ。ノードもボタンや表と同じ意味tokenで描かれるMakeNodeStyle(theme)Gallery の既存 world（blueprint, pastel-pop, sticker）がノードにもそのまま効く
2. スタイルNodeStyle の値、カテゴリ表、ノード単位の上書きを渡すNodeStyle, NodeCategoryStyle, NodeView::tint, PushNodeStyleシェーダー系は緑、テクスチャ系は橙、入力は赤のヘッダーにする
3. 描画フック部位ごとの描画関数を差し込み、false を返した部位は既定描画に戻るNodeDrawHooks（背景・ヘッダー・ピン・配線）ヘッダーに画像を敷く、独自のピン図形を描く、配線に模様を付ける

描画フックは Skin と同じ流儀にします。関数ポインタと void* user を受け取り、ライブラリは所有しません。渡すのは位置、大きさ、ズーム、状態（hover・選択・接続中・無効）と解決済みの色で、ホストは公開DrawListに描きます。入力処理とIDはライブラリ側に残るので、フックを入れても選択、ドラッグ、接続の動作は変わりません。

API案

既存の型の末尾に項目を足し、既定値では現在に近い見た目を保ちます。緑が新規です。名前は案です。

// ノードの形。NodeKind（グラフ上の意味）とは別に、見た目だけを決める。
enum class NodeShape { Standard, Event, Compact, Variable, Reroute, Comment, Note };
enum class HeaderFill { Flat, Tinted, Gradient, Strip, None };

struct NodeCategoryStyle {      // カテゴリIDから色を引く表。ホストが所有して貸し出す
    std::uint64_t id = 0;
    ImVec4 header{}, accent{};
    std::string_view icon{};
};

struct NodeView {
    ...既存の項目...
    NodeShape shape = NodeShape::Standard;
    std::uint64_t category = 0;     // NodeCategoryStyle を引く
    ImVec4 tint{};                  // alpha 0 ならカテゴリ→テーマの順に継承
    std::string_view subtitle{}, glyph{};  // ヘッダー右の補足、Compact の中央記号
    bool hideUnusedPins = false;
};

enum class PinRole { Data, Flow };
enum class PinContainer { Single, Array, Set, Map };
enum PinFlags : std::uint32_t { PinFlags_None = 0, PinFlags_Reference = 1, PinFlags_Wildcard = 2,
                               PinFlags_Field = 4, PinFlags_MultiInput = 8, PinFlags_Optional = 16 };
struct PinView {
    ...既存の項目...
    PinRole role = PinRole::Data;
    PinContainer container = PinContainer::Single;
    std::uint32_t flags = PinFlags_None;
    std::uint64_t panel = 0;        // 所属する折りたたみパネル
};

enum class LinkColorSource { OutputType, InputType, Gradient, Accent };
enum class LinkArrow { None, Middle, End };
struct NodeStyle {
    ...既存の項目...
    float hoverBorderWidth = 1.5f, selectedBorderWidth = 2;
    HeaderFill headerFill = HeaderFill::Strip;   // 現行の「上端の線」
    bool hollowUnconnectedPins = false;
    float flowLinkWidth = 3.5f;
    LinkColorSource linkColor = LinkColorSource::OutputType;
    LinkArrow linkArrow = LinkArrow::Middle;
    bool highlightConnectedLinks = true;
    float flowSpeed = 1, flowSpacing = 14;
    StatusDisplay status = StatusDisplay::WhenActive;  // Idle かつ 0ms なら出さない
    std::span<const NodeCategoryStyle> categories{};
    const NodeDrawHooks *hooks = nullptr;
};

// 描画フック。false を返すと既定の描画に戻る。入力とIDはライブラリが保持する。
struct NodeChromeView { const NodeView *node; ImVec2 min, max; float zoom, headerHeight;
                         ImVec4 header, surface, border; bool hovered, selected, disabled; };
struct PinChromeView  { const PinView *pin; ImVec2 center; float radius; ImVec4 color;
                         bool connected, hovered, candidate; };
struct LinkChromeView { const LinkView *link; std::span<const ImVec2> points; ImVec4 from, to;
                         float width; bool hovered, selected, flowing; };
struct NodeDrawHooks {
    void *user = nullptr;
    bool (*background)(ImDrawList *, const NodeChromeView &, void *) = nullptr;
    bool (*header)(ImDrawList *, const NodeChromeView &, void *) = nullptr;
    bool (*pin)(ImDrawList *, const PinChromeView &, void *) = nullptr;
    bool (*link)(ImDrawList *, const LinkChromeView &, void *) = nullptr;
};

// 新しい部品
bool BeginNodePanel(EditorFrame &frame, std::uint64_t panel, std::string_view label, bool *open);
void EndNodePanel(EditorFrame &frame);
void PushNodeStyle(EditorFrame &frame, const NodeStyle &style);   // 以降のノードに適用
void PopNodeStyle(EditorFrame &frame);
bool InsertReroute(EditorFrame &frame, LinkId link, Point at);    // 要求を積むだけ
NodeStyle MakeNodeStylePreset(const Theme &theme, NodeStylePreset preset);

確認事項

実装に入る前に、次の4点を決めてください。

  1. ABI の扱い。NodeView・PinView・NodeStyle の末尾に項目を足すと、構造体の大きさが変わります。node_editor は「development API」扱いなので許容する案です。
  2. 既定の見た目を変えてよいか。ステータス行を「Idle かつ 0ms なら非表示」にし、配線の既定色を型色にすると、既存ホストの見た目が変わります。現行の見た目を保つ設定も残します。
  3. プリセットの置き場所。Material / Script / Classic をライブラリの関数にするか、Gallery の例コードに留めるか。汎用の出発点なのでライブラリ側を推奨します。
  4. 着手範囲。Phase 1 から順に進めるか、Unreal 系の実行フロー（Phase 3）を先に行うか。
